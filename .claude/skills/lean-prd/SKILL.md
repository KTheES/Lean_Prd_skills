# lean-prd — BML 기반 린스타트업 PRD 생성기

## 이 스킬이 하는 일

전통 PRD처럼 만들 기능부터 나열하지 말고, 가장 위험한 가정과 배워야 할 것을 먼저 정한 뒤 그 학습에 필요한 최소 범위만 설계한다. 가설 ID로 연결되지 않는 기능·지표·마일스톤은 검증에 기여하지 않는 낭비 후보로 취급한다. 결과는 각자 독립적으로 읽히면서도 ID와 수치가 일치하는 12개 Markdown 파일이다.

ID 네임스페이스는 가설 `H#`, 지표 `M#`, 실험 `E#`, 마일스톤 `MS0`~`MS3`, Pivot 옵션 `P#`, 트리거 `T#`로 고정한다.

## 참조 자료를 읽는 시점

- 생성·cycle 순서와 판단이 필요하면 `references/bml-cycle.md`를 먼저 읽는다.
- 파일명, 필수 헤딩, 표 열을 채우기 전에 `references/prd-section-guide.md`를 읽는다.
- `03-solution-and-mvp.md`와 `09-milestones.md` 작성 전에 `references/mvp-and-milestone-guide.md`를 읽는다.
- `07-team.md`와 `08-tech-stack.md` 작성 전에 `references/team-and-tech-stack-guide.md`를 읽는다.

## 두 가지 모드

| 모드 | 조건 | 결과 |
|---|---|---|
| generate | `docs/prd/`에 규격 파일이 없거나, 사용자가 새 아이디어의 PRD 생성을 요청 | 템플릿을 기반으로 12개 파일 생성 |
| cycle | 12개 파일과 `11-bml-log.md`가 있고 사용자가 cycle, 실험 결과, Pivot/Persevere/Kill 반영을 요청 | Cycle N 추가, 결정 제안, 승인된 결정에 맞춰 관련 문서 갱신 |

## generate 모드

### 1단계. 입력 수집

아이디어 한 줄만 받았다면 아래 질문을 한 번에 최대 5개 묻는다. 왕복을 줄이되, 답을 꾸며 내지 않기 위해 한 번에 묻는다.

1. 제품명과 한 줄 아이디어, 현재 대안은 무엇인가?
2. 첫 잠재고객 10명은 누구이며 어떤 채널로 접촉 가능한가?
3. 이미 확보한 실제 데이터와 재사용할 코드·자산은 무엇인가?
4. 팀 규모·주당 투입 시간·월 예산·전체 기간은 얼마인가?
5. 플랫폼 제약과 가장 걱정되는 가정은 무엇인가?

답이 없으면 1인, 주 20시간, 월 5만 원, 8주, 반응형 웹, 실제 데이터 없음, 접근 채널 미확정으로 가정한다. 이 가정은 `00-overview.md` 상단과 `11-bml-log.md` Cycle 0에 표시한다. 가정과 사실을 구분해야 이후 학습이 무엇을 바꿨는지 추적할 수 있다.

### 2단계. 생성 순서

BML은 Build→Measure→Learn으로 실행하지만 계획은 Learn→Measure→Build로 역산한다. 먼저 무엇을 배울지 가설로 고정하고, 판단할 수치와 이를 측정하는 최소 제품을 정해야 결과를 본 뒤 기준을 바꾸는 오류를 피할 수 있다. `00-overview.md`는 다른 문서의 요약이므로 새 정보를 만들지 않고 마지막에 쓴다.

| 순서 | 파일 | 이 단계에서 확정되는 것 |
|---|---|---|
| ① | `01-problem-and-hypotheses.md`, `02-target-customer.md` | H#, 위험도 순위, 얼리어답터 |
| ② | `05-metrics.md` | H#별 M#, 계산식, 목표·실패 기준 |
| ③ | `03-solution-and-mvp.md`, `04-requirements.md` | MVP 유형, In/Out, 수용 기준, 측정 장치 |
| ④ | `06-experiment-plan.md` | E#, Build/Measure/Learn, 샘플과 회색 지대 |
| ⑤ | `07-team.md`, `08-tech-stack.md` | 다음 실험에 필요한 최소 인력·스택 |
| ⑥ | `09-milestones.md` | MS0~MS3 검증 순서와 숫자 종료 조건 |
| ⑦ | `10-risks-and-pivot.md` | T#, P#, Kill 조건 |
| ⑧ | `11-bml-log.md`, `00-overview.md` | 초기 가정 스냅샷과 전체 요약 |

각 파일은 `assets/prd-templates/<파일명>`을 복사해 채운다. 필수 헤딩과 표 열을 유지한다.

### 3단계. 파일별 작성 규칙

**가설(01)**

- 가치 가설을 성장 가설보다 먼저 두고, 검증 가능한 행동·M#·숫자 목표를 한 문장에 넣는다.
- 불확실성과 치명도를 각각 1~5로 평가하고 곱으로 정렬한다. 가장 높은 가설을 MS0와 E1에 둔다.
- 근거가 없는 수치는 가정임을 표시한다. 리스크 순위는 듣기 좋은 기능보다 먼저 검증할 대상을 정하기 위해 사용한다.

**지표(05)**

- 모든 H#에 최소 하나의 Actionable M#를 연결하고 계산식·이벤트·코호트·목표 근거를 적는다.
- 누적 조회수 같은 Vanity 지표는 보지 않을 이유와 대신 볼 지표를 쓴다.
- 근거가 약한 목표는 `초기 가정—Cycle 1 후 보정`으로 표시하며 결과를 본 뒤 임계값을 바꾸지 않는다.

**MVP(03)**

- Landing page, Demo video, Concierge, Wizard of Oz, Single-feature, Piecemeal 중 가설을 가장 싸게 검증하는 유형을 고른다.
- In은 H# 연결 또는 측정 장치·최소 동작 예외 사유가 있어야 한다. Out에는 재검토 조건을 적는다.
- 1인 10영업일을 넘기면 낮은 리스크 가설의 기능부터 Out으로 옮긴다. 성공 기준은 05의 M# 목표를 그대로 인용한다.

**요구사항(04)**

- 사용자 스토리와 Must는 03의 In 범위만 포함한다. 각 스토리에 Given/When/Then 수용 기준을 둔다.
- 성능·보안/개인정보·접근성·분석 이벤트를 수치 또는 검증 가능한 문장으로 정의한다.
- 이벤트 이름은 소문자 `snake_case`로 쓰며 05의 이벤트 표와 일치시킨다.

**실험(06)**

- H#별 E# 블록에 Build, Measure, Learn을 모두 쓴다. Measure에는 M#, 수집법, 샘플, 기간을 포함한다.
- 통과 기준은 05 목표와 같게 하고 별도의 실패 기준과 회색 지대 처리 규칙을 사전에 고정한다.
- 작은 표본이면 통계적 유의성을 주장하지 말고 정성 탐색 단계임을 밝힌다.

**팀(07)**

- 역할·책임·구체 기술·FTE·담당 MS·충원 상태를 작성하고 마일스톤 통과에 따른 합류 조건을 둔다.
- 1인 프로젝트는 본인 커버, 도구 대체, 외주·채용을 구분한다.
- 지표 리뷰 주기, 결정 주체, 불일치 시 T# 우선 규칙, 실험 WIP 제한을 명시한다.

**기술 스택(08)**

- 모든 계층에 선택, MVP 근거, 대안과 기각 이유, 월 비용, 전환 조건의 6열을 채운다.
- 가격·한도는 공식 URL과 확인일을 적고 확인하지 못했으면 `확인 필요`로 둔다. 사실을 추측하지 않는다.
- 아키텍처 Mermaid, 분석·Feature Flag, ADR 1개 이상, 지금 하지 않을 것 3개 이상을 포함한다.

**마일스톤(09)**

- MS0~MS3을 기능 묶음이 아니라 문제→가치→리텐션→성장 검증 단위로 설계한다.
- 각 MS에 H#, 최소 산출물, M# 숫자 종료 조건, Go, No-Go와 P#, 담당을 둔다.
- GitHub Milestone·Issue·Project 매핑과 Mermaid 일정을 포함한다.

**Pivot(10)**

- T#는 `M# < 값이 N사이클 연속`처럼 숫자로 정의한다.
- P#는 Pivot 유형뿐 아니라 유지·폐기 범위와 예상 비용을 제품 맥락에서 구체화한다.
- 세그먼트 또는 비전 자체가 연속으로 기각되는 경우를 Kill 조건으로 사전 정의한다.

**로그(11)**

- Cycle 0에 기본 가정, H# 스냅샷, 제공된 기존 데이터, E1을 기록한다.
- 실제 사용자 데이터가 없으면 없다고 쓰고, 가상 데이터를 실제처럼 표현하지 않는다.
- 검토 메모는 사람이 확인한 내용만 기록한다. 생성 시 사람 검토 항목은 `TODO(사람 검토)`로 남긴다.

**개요(00)**

- `[고객]이 [문제]를 겪을 때 [제품]으로 [결과]를 얻는다` 형식으로 쓴다.
- Lean Canvas 9칸은 이미 작성한 문서만 2줄 이내로 요약하고 상세 링크를 둔다.
- 마지막에 써야 개요가 가설·수치·범위와 어긋나는 것을 막을 수 있다.

### 4단계. 교차 참조 검사

파일 분리는 변경 diff를 작게 만들지만 중복 수치가 어긋날 수 있으므로 저장 전에 다음을 확인한다.

1. 01의 모든 H#가 05의 M#, 06의 E#, 09의 MS#, 10의 P#/T#에서 참조되는가?
2. 03 성공 기준, 05 목표, 06 통과 임계값, 09 종료 조건의 M#와 숫자가 동일한가?
3. 03의 In과 04의 Must가 동일하며 각 항목에 H# 또는 예외 사유가 있는가?
4. 04와 05의 분석 이벤트 이름과 속성이 일치하는가?
5. MS0가 최고 위험 가설을 다루고 모든 No-Go P#가 10에 정의되어 있는가?
6. 07의 담당·합류 조건이 09의 담당·Go 조건과 모순되지 않는가?
7. 08의 비용 합계가 입력 예산 안이고 모든 외부 사실에 출처·확인일이 있는가?

### 5단계. 검증

```bash
python3 .claude/skills/lean-prd/scripts/validate_prd.py docs/prd
```

실패하면 개별 문서만 임시로 땜질하지 말고 누락을 만든 SKILL.md·템플릿 규칙을 먼저 개선한 뒤 영향을 받는 문서를 재생성한다. 최종 표준 출력을 `docs/prd/VALIDATION.txt`에 저장한다. 스크립트가 잡지 못하는 가설 품질, 가격 사실성, 목표의 현실성은 사람 검토 대상으로 남긴다.

### 6단계. 보고

12개 생성 여부, 검증 FAIL/WARN 수, 사람에게 남은 사실 확인·실험 수집·검토 항목을 보고한다. 미확인 사실이나 사용자 반응을 완료된 것처럼 보고하지 않는다.

## cycle 모드

1. 대상 H#/E#, 측정 M#, 표본 수, 결과값, 익명화한 정성 피드백과 증빙 경로를 확인한다.
2. 06에 사전 정의된 통과·실패·회색 지대와 결과를 비교한다. 결과를 받은 뒤 기준을 바꾸지 않는다.
3. 수치상 결정을 제안하되 최종 Pivot/Persevere/Kill은 제품 책임자가 승인하게 한다. 작은 표본과 맥락을 기계 규칙만으로 확정할 수 없기 때문이다.
4. `references/bml-cycle.md` §4 형식으로 Cycle N을 11에 추가하고 실제·가상·미확인을 구분한다.
5. 승인된 결정에 따라 아래 문서를 갱신하고 전체 교차 참조·검증을 다시 실행한다.

| 결정 | 갱신 파일 | 내용 |
|---|---|---|
| Persevere | 06, 09, 11 | 다음 E#/MS 활성화, 학습·근거 기록 |
| Pivot | 01, 02 또는 03, 04, 05, 06, 09, 10, 11, 마지막에 00 | P#에 맞춰 가설·세그먼트/범위·수치·계획 재정렬 |
| Kill | 09, 10, 11, 00 | 중단 조건 충족 근거, 후속 실험 중지, 보존할 학습 기록 |
| 재실험 | 06, 09, 11 | 표본·변수·기간만 조정하되 사전 기준 변경 이유와 버전 기록 |

## 하지 말 것

- 결과를 본 뒤 통과 기준을 낮추지 않는다. 사후 기준은 모든 실험을 성공처럼 보이게 한다.
- 가설 없는 기능을 호의로 In에 넣지 않는다. 개발량은 늘고 배움은 늘지 않는다.
- 사람 검토·최종 결정을 에이전트가 대신 완료 처리하지 않는다. 제출물에는 실제 검토 흔적이 필요하다.
- 특정 제품명·API·도구·도메인을 SKILL.md 본문에 하드코딩하지 않는다. 필요한 예시는 `references/`에만 "예시"로 표기해 둔다. 어떤 아이디어를 넣어도 12개 파일이 생성되어야 하며(재사용성), 특정 도메인에 과적합되면 다른 입력에서 섹션이 누락된다.
- 법적 쟁점이 될 수 있는 내용은 "쟁점 가능성"과 "전문가 확인 필요"까지만 쓰고, 법적 결론(침해 여부, 합법/불법)을 단정하지 않는다. AI는 법률 판단 주체가 아니며, 단정은 사용자의 오판과 제품의 책임 문제로 이어진다.
- 가격·시장 규모·비용 수치는 출처 URL과 확인 일자가 함께 있는 값만 쓴다. 공식 출처를 확인하지 않은 가격·법률·시장 수치를 사실처럼 쓰지 않는다. 확인하지 못했으면 숫자를 쓰지 않고 "확인 필요"로 표시한다. 임의의 수는 지표·예산·마일스톤의 임계값을 오염시키고, 실험 후에 기준을 바꾸는 것과 같은 신뢰 손실을 만든다.
- 실사용자 데이터·인터뷰 인용을 지어내지 않는다. 거짓 증빙은 학습과 평가를 모두 훼손한다. 사용자 반응·인터뷰·지표 값을 추정해서 채우지 않는다. 데이터가 없으면 "미측정"으로 두고, 가상 데이터를 쓸 때는 "가상"임과 생성 근거를 명시한다.
