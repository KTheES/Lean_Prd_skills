# PRD 목차별 작성 가이드 (필수 헤딩 규격)

`scripts/validate_prd.py`는 이 문서의 **필수 헤딩**을 검사합니다. 헤딩 텍스트는 정확히 일치해야 합니다 (레벨 `##`, 번호 포함). 템플릿은 `assets/prd-templates/`에 있습니다.

## 공통 헤더 (모든 파일)

파일 첫 줄은 `# <순번>. <섹션 제목>` 이고, 그 아래 메타 블록이 옵니다.

```
# 03. 솔루션과 MVP

| 제품 | 버전 | 최종 수정 | 관련 가설 |
|---|---|---|---|
| FocusFirst | 0.2 | 2026-11-05 | H1, H2 |
```

관련 가설이 없는 파일(07, 08)은 "—" 대신 "전체"라고 씁니다.

---

## 00-overview.md — 제품 개요

필수 헤딩: `## 1. 한 줄 정의` · `## 2. 비전과 현재 단계` · `## 3. Lean Canvas 요약` · `## 4. 문서 맵`

- 한 줄 정의는 "**[고객]**이 **[문제]**를 겪을 때 **[제품]**으로 **[결과]**를 얻는다" 형식.
- Lean Canvas 9칸(문제 / 고객 세그먼트 / 고유 가치 제안 / 솔루션 / 채널 / 수익 흐름 / 비용 구조 / 핵심 지표 / 경쟁 우위)을 표로. 각 칸 2줄 이내. 상세는 해당 파일로 링크.
- 문서 맵은 12개 파일의 역할을 한 줄씩. 다른 파일을 **마지막에** 요약하므로 00은 가장 나중에 생성.

## 01-problem-and-hypotheses.md — 문제와 가설

필수 헤딩: `## 1. 문제 정의` · `## 2. 현재 대안과 한계` · `## 3. 가설 목록` · `## 4. 가장 위험한 가정 순위`

- 가설 표 열: `ID | 유형(가치/성장) | 가설 문장 | 검증 지표(M#) | 불확실성(1~5) | 치명도(1~5) | 우선순위`
- 가설 문장 형식: "우리는 **[고객]**이 **[상황]**에서 **[행동]**할 것이라고 믿는다. **[지표]**가 **[목표]**이면 참이다."
- ID는 `H1`부터 순번. 다른 파일에서 이 ID로만 참조합니다.

## 02-target-customer.md — 타깃 고객

필수 헤딩: `## 1. 고객 세그먼트` · `## 2. 얼리어답터 페르소나` · `## 3. 접근 채널과 첫 10명`

- 페르소나는 1~2명. 이름·상황·현재 해결 방법·불만·"이 제품을 쓸 트리거 순간".
- "첫 10명"은 실제로 연락 가능한 집단(학과 단톡, 특정 커뮤니티, 지인 N명)으로.

## 03-solution-and-mvp.md — 솔루션과 MVP

필수 헤딩: `## 1. 솔루션 개요` · `## 2. MVP 유형과 선택 이유` · `## 3. MVP 범위 (In / Out)` · `## 4. MVP 성공 기준`

- MVP 유형: Landing page / Demo video / Concierge / Wizard of Oz / Single-feature / Piecemeal 중 선택, 이유 3줄.
- In/Out 표 열: `기능 | In/Out | 검증 가설(H#) | 비고(Out이면 '나중에 하는 이유')`. In 항목에 H#가 없으면 Out으로 옮깁니다.
- 성공 기준은 `05-metrics.md`의 M# 목표치를 그대로 인용. 숫자 필수.
- 1인 기준 구축 기간 2주 이하. 넘으면 In을 줄입니다.

## 04-requirements.md — 요구사항

필수 헤딩: `## 1. 사용자 스토리` · `## 2. 기능 요구사항` · `## 3. 비기능 요구사항` · `## 4. 우선순위 (MoSCoW)`

- 사용자 스토리는 MVP In 범위만. "~로서 ~하고 싶다, 그래야 ~" 형식에 **수용 기준** 1개 이상.
- 비기능: 성능, 보안/개인정보, 접근성, 분석 이벤트 트래킹(어떤 이벤트를 어떤 이름으로 보낼지 — 05와 연결).
- MoSCoW의 Must는 03의 In과 동일해야 합니다.

## 05-metrics.md — 지표

필수 헤딩: `## 1. North Star Metric` · `## 2. AARRR 지표` · `## 3. Actionable vs Vanity` · `## 4. 측정 방법과 이벤트`

- 지표 표 열: `ID | 단계(AARRR) | 지표 | 정의(계산식) | 현재/기준값 | 목표(MVP) | 검증 가설(H#)`
- ID는 `M1`부터. 모든 가설에 최소 1개 지표. 아직 가설이 없는 단계(보통 Revenue)는 검증 가설 열 "—", 목표 열 "측정만"으로 두면 검증 스크립트가 숫자 목표를 요구하지 않는다.
- 마일스톤 ID는 `MS#`다. `M#`는 지표에만 쓴다.
- Vanity 섹션에는 "우리가 보고 싶지만 보지 않을 숫자"를 적고 이유를 씁니다 (누적 가입자, 페이지뷰 등).
- 측정 방법: 어떤 도구(PostHog, Amplitude, GA4, 수동 스프레드시트)로 어떤 이벤트 이름을 수집하는지. 04의 이벤트 이름과 일치.

## 06-experiment-plan.md — 실험 계획

필수 헤딩: `## 1. 실험 우선순위` · `## 2. 실험 설계` · `## 3. 판단 기준` · `## 4. 일정과 샘플`

- 가설별 실험 블록: `### E1 — H# 검증` 아래 Build(무엇을/얼마나) · Measure(M#, 수집 방법) · Learn(결과 해석 규칙).
- 판단 기준 표 열: `실험 | 지표 | 통과 ≥ | 실패 < | 회색 지대 처리`. 숫자는 05의 목표치와 일치.
- 샘플 크기와 기간: 통계적 유의성을 주장하려면 근거(최소 표본 계산 또는 "정성 검증 단계라 N=10"이라는 명시).

## 07-team.md — 팀

필수 헤딩: `## 1. 역할과 책임` · `## 2. 마일스톤별 팀 구성` · `## 3. 채용 / 외주 우선순위` · `## 4. 의사결정 규칙`

- 역할 표 열: `역할 | 책임 | 필요 역량(구체 기술) | 투입(FTE) | 담당 마일스톤 | 현재 충원 상태`
- 마일스톤별 구성: MS0에는 몇 명, MS2에는 몇 명 — 팀이 어떻게 커지는지.
- 의사결정 규칙에 Pivot/Persevere 결정 주기·주체·동률 시 규칙 포함.
- 1인 프로젝트: "본인 커버 / 도구로 대체 / 외주·채용 필요"로 나눠 작성.

## 08-tech-stack.md — 기술 스택

필수 헤딩: `## 1. 아키텍처 개요` · `## 2. 계층별 스택` · `## 3. 분석 · 실험 · Feature Flag` · `## 4. 지금 하지 않을 것`

- 계층별 표 열(6열 필수): `계층 | 선택 | 선택 근거(MVP 관점) | 검토한 대안 | 월 비용(예상) | 리스크 / 전환 조건`
- 계층: 프론트엔드, 백엔드/API, 데이터, 인증, 호스팅/배포, 분석·실험, CI/CD (+ AI/ML 등 도메인 필요 시).
- 비용·기능은 출처 URL과 확인 일자.
- "지금 하지 않을 것"은 최소 3개, 각각 "언제 다시 검토할지" 조건.
- 상세 가이드: `team-and-tech-stack-guide.md`.

## 09-milestones.md — 마일스톤

필수 헤딩: `## 1. 마일스톤 개요` · `## 2. 마일스톤 상세` · `## 3. GitHub 매핑` · `## 4. 일정`

- 개요 표 열: `ID | 이름 | 기간 | 검증 가설(H#) | 핵심 산출물 | 종료 조건(M# 목표) | No-Go 시`
- MS0~MS3, 각 2주. MS0는 가장 위험한 가설. 전체 기간이 8주보다 짧으면 마일스톤을 빼지 말고 기간을 압축한다 (`mvp-and-milestone-guide.md` §2.2).
- 상세 블록 `### MS0 — <이름>`: 산출물 / 종료 조건 / Go-No-Go 판단 / 담당(07 참조).
- GitHub 매핑: Milestone 이름, 라벨, Projects 칼럼 (강의 Section 08).
- 일정은 Mermaid gantt 권장.

## 10-risks-and-pivot.md — 리스크와 Pivot

필수 헤딩: `## 1. 리스크 레지스터` · `## 2. Pivot 트리거` · `## 3. 사전 정의된 Pivot 옵션` · `## 4. Kill 조건`

- 리스크 표 열: `ID | 리스크 | 발생 가능성 | 영향 | 대응 | 관련 가설`
- Pivot 트리거: "M# 지표가 X 미만이 2사이클 연속" 같은 **숫자 조건**.
- Pivot 옵션: Zoom-in / Zoom-out / Customer Segment / Platform / Business Architecture 등 유형별로 "우리 제품에서는 구체적으로 무엇"인지.
- Kill 조건: 비전 자체가 틀렸다고 판단할 조건.

## 11-bml-log.md — BML 로그

필수 헤딩: `## 사이클 요약` · `## 검토 메모`

- 사이클 블록 형식은 `bml-cycle.md` §4. 사이클이 없을 때도 `## Cycle 0 — 초기 가정` 블록을 둡니다 (PRD 생성 시점의 가정 스냅샷).
- 검토 메모: 사람이 AI 초안을 검토하며 고친 내용. 날짜·파일·무엇을 왜. 생성 시점에는 표 헤더만 두고 행은 비운다 (스크립트 WARN 1개가 정상).
